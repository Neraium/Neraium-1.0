# PRD: Generic Telemetry Connection and Ingestion

> Description: Add a production, customer-agnostic, read-only framework that securely connects operational telemetry sources, explicitly maps their signals into Neraium's canonical model, continuously ingests normalized observations, and hands source-neutral windows to the existing analysis engine.
> Author: user
> Date: 2026-08-25
> Status: approved — implementation authorized 2026-08-25
> Mode: feature

## Problem

Neraium can analyze historical uploads and already contains partial connector, live-telemetry, normalization, quality, evidence, and worker mechanisms, but these paths are globally scoped, inconsistently persisted, and unsafe as a multi-tenant production connection surface. A real customer needs to connect a read-only source once, discover and intentionally map its signals, receive continuously normalized and quality-classified data, observe connection health, backfill a bounded history, and feed the same authoritative SII analysis without vendor schemas or synthetic upload identities. This milestone must converge the reusable paths around one canonical, tenant-scoped model rather than add another ingestion architecture.

## Users

- **Authorized customer operators and engineers:** configure sources, submit credentials one way, validate connectivity, discover and map signals, enable ingestion/backfill, and diagnose health without seeing secret material.
- **Neraium operations and connector developers:** operate the ingestion worker, investigate bounded sanitized failures, monitor quality and throughput, and add read-only providers behind a stable contract.

## Core Features

1. **Tenant-scoped connection lifecycle:** Authorized users can create, validate, enable, disable, inspect, retry, archive, and audit facility-bound data connections whose credentials remain behind an opaque secure-secret abstraction.
2. **Safe extensible source access:** A server-side read-only connector contract supports discovery, bounded backfill, polling, health, checkpoints, retries, rate limits, and capability reporting, with a production generic HTTPS GET provider and a server-owned historian/database template boundary.
3. **Canonical registry and normalization:** Discovered external tags remain traceable and unmapped until explicitly associated with the facility/system/asset hierarchy and a canonical signal concept, after which supported units and source timestamps are explicitly normalized with provenance and quality classification.
4. **Durable ingestion and analysis handoff:** A PostgreSQL-backed worker uses transactional leases, idempotent batches, partial-failure quarantine, checkpoints, bounded backoff, resumable backfill, and source-neutral canonical windows that invoke the existing authoritative SII engine exactly once.
5. **Production Data Connections workspace:** The existing Data Connections area provides a restrained responsive wizard plus connection, signal-mapping, health, freshness, ingestion-run, and sanitized-error views while preserving the separate historical upload workflow.

## Out of Scope (v1)

- Direct BACnet, Modbus, PLC, OPC UA, or actuator access; setpoint changes; acknowledgements; API writes; SQL mutations; arbitrary command execution; and every other control-path primitive are prohibited because Neraium remains read-only and above the OT control layer.
- Customer-, facility-, resort-, BAS-, historian-, equipment-manufacturer-, or vendor-specific schemas, fixtures, hard-coded mappings, required tags, dashboards, or connector logic.
- Automatic semantic mapping or unit guessing as authority; suggestions may be added later only when confidence and provenance are explicit and an authorized person must approve them.
- A browser-configured raw SQL, DSN, SQLite path, HTTP method/body, arbitrary header, proxy, or unrestricted private-network connector; private sources require a later approved VPN, PrivateLink, site agent, tunnel, or named network-profile deployment.
- A universal industrial protocol platform, generic streaming broker implementation, SQS/FIFO redesign, or premature time-series database; v1 provides one real public-HTTPS polling/backfill slice and capability boundaries for future providers.
- Replacement or expansion of the historical/manual-upload workflow, rewrite of SII/behavioral models, automatic creation of findings for ineligible data, or migration of ambiguous global legacy telemetry into a tenant.
- Secret retrieval by the browser, routine secret deletion, logging of credentials or raw sensitive payloads, and exposure of secret identifiers/ARNs in connection, audit, error, or health responses.
- Automatic infrastructure deployment, production network peering, dynamic Secrets Manager IAM before it is explicitly approved, or destructive removal of compatibility routes and legacy tables in this milestone.

## Technical Decisions

- **Canonical persistence and scope:** Introduce additive relational telemetry tables in the shared PostgreSQL application store, keyed by the server-attested `AuthenticatedPhase4Scope.resource_scope_id` for an authorized facility workspace rather than the user-dependent `DatasetScope.storage_id`, because shared operators must see one facility authority and role-local SQLite/EFS cannot enforce cross-replica leases or multi-tenant identity; personal/free-form workspaces cannot create production connections and ambiguous legacy rows remain quarantined and analysis-ineligible.
- **Hierarchy identity:** Store canonical `asset_id` while accepting the current `equipment_id` through one explicit asset-compatibility contract because a second physical-equipment identity would fragment analysis and lineage.
- **Connector boundary:** Extend the existing provider registry into a read-only capability contract and make generic public HTTPS GET the first production adapter because it delivers a useful vertical slice without placing Neraium in the OT control path.
- **Network safety:** Centralize an HTTPS/443 public-egress policy with DNS/IP validation on every request, redirects disabled, same-origin cursor pagination, environment proxies disabled, strict budgets, and a production controlled-egress requirement because application URL parsing alone cannot fully mitigate SSRF and DNS rebinding.
- **Historian/database boundary:** Retain only server-owned query-template and approved-network-profile identifiers with typed bounded parameters because accepting browser-provided SQL, DSNs, or filesystem paths cannot meet the read-only or SSRF boundary.
- **Secrets:** Persist only an internal opaque secret handle and return only `credentials_configured` plus safe version/update metadata because secret contents and references must never leave the service; support pre-provisioned references first and dynamic one-way writes only through the abstraction after least-privilege IAM is approved.
- **Scheduling:** Claim due connections in PostgreSQL with expiring transactional leases, persisted checkpoints, and bounded jittered backoff because process locks and role-local storage cannot prevent overlap or recover safely after worker restarts.
- **Analysis seam:** Build canonical analysis windows by authoritative tenant/workspace/facility/system/asset scope and call the existing SII orchestration exactly once because analysis must be source-neutral and the current upload/SII call cardinality is an established invariant.
- **Dependencies:** Prefer the repository's existing FastAPI, Pydantic, HTTP client, PostgreSQL, React, pytest, Vitest, and Playwright dependencies; add a dependency only if the implementation proves the locked stack cannot securely provide DNS/IP validation, unit conversion, or PostgreSQL coordination.

## Architecture

Production connection, signal, mapping, run, checkpoint, health, audit, quarantine, observation, and lineage state lives in additive tenant-scoped PostgreSQL tables, with durable authority keyed by the server-attested Phase 4 resource scope for an authorized facility workspace rather than a current operator identity, request payload, or source data. Existing connector providers are adapted to a common retrieval-only contract; the first enabled provider is a centrally hardened public-HTTPS GET adapter, while historian/database access remains a server-owned template/provider boundary. Every discovered source signal is registered and remains analysis-ineligible until an authorized mapping resolves hierarchy, canonical concept, and explicit unit policy, after which one reusable ingestion pipeline normalizes timestamps/units, classifies quality, deduplicates, quarantines per-record failures, persists lineage, and advances checkpoints transactionally. Worker-owned leases schedule incremental reads and bounded resumable backfills, and eligible canonical windows carry validated `AuthenticatedPhase4Scope` plus server-bound system identity into a source-neutral adapter that invokes the existing SII orchestration exactly once. `DataConnectionsWorkspace` first extracts its upload-only state into a stable Historical Import seam, then manages the connection lifecycle beside it.

## Acceptance Boundaries

- The authoritative hierarchy is `tenant/workspace -> facility -> system -> asset -> signal`; external payload hierarchy is retained only as lineage metadata and cannot select or override server scope.
- Production connections require an active explicit facility workspace and use its `AuthenticatedPhase4Scope.resource_scope_id` as durable authority; `user_id` is audit attribution only, and personal/free-form workspaces cannot create production connections.
- An observation preserves connection, ingestion run, external tag, source timestamp/offset/timezone, original value/unit, canonical signal, normalized UTC timestamp/value/unit, conversion version, quality state, and mapping provenance.
- Supported quality states distinguish transport/format/mapping quality (`good`, `stale`, `missing`, `invalid_value`, `duplicate`, `unit_unresolved`, `timestamp_invalid`, `mapping_required`, and quarantined format/range failures) from unusual but valid sensor behavior.
- A connection is not shown as healthy merely because authentication once succeeded; reachability, authentication, arrival/freshness, mapping completeness, acceptable data quality, and worker/checkpoint state are separate health facets.
- Unmapped, incompatible-unit, invalid-timestamp, unauthorized-scope, and quarantined observations never become analysis eligible; unusual-but-valid values can remain eligible for SII interpretation.

## Open Questions and Approval Gates

- **Architecture approval:** Approve shared PostgreSQL keyed by the explicit facility workspace's Phase 4 `resource_scope_id`, `asset_id` through an `equipment_id` compatibility contract, fail-closed legacy quarantine, the central public-HTTPS policy, transactional worker leases, and the exact source-neutral Phase 4 scope/system-bound single-SII-call seam before Phase 3 implementation.
- **Infrastructure approval:** Dynamic secret creation remains disabled until scoped Secrets Manager IAM, ownership tags, API/worker role separation, and the `neraium/{environment}/telemetry-connections/*` namespace are reviewed; pre-provisioned secret references are the supported interim production path.
- **Deployment approval:** Production enablement is blocked until controlled outbound egress is deployed and verified; private customer networks require a separately approved connectivity pattern and cannot be made reachable by relaxing the public connector policy.
- **Retention approval:** Initial observation retention and partition/archival thresholds must be selected from measured production cadence before broad rollout; v1 documents and monitors the boundary without prematurely introducing a new time-series platform.
