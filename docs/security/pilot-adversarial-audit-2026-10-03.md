## Implemented architecture and trust boundaries

1. Internet/customer browser → separately hosted React frontend (`frontend/src/services/api/authApi.js`, API clients) → HTTPS API/ALB in retained production profile → FastAPI (`backend/app/main.py`). Cookies, request bodies, workspace selectors and object IDs cross an untrusted-client boundary. Frontend builds do not inject a shared bearer; the email marker and some analytical history/notes use localStorage. API headers do not establish headers on the separately hosted frontend.
2. API → `core/security.py:require_api_access` → session lookup in `services/auth_store.py` or configured service bearer → role gates → `workspace_authorization.py:resolve_workspace_context`. Explicit facilities require active membership; service tokens require exact workspace allowlisting. Personal scope derives from authenticated identity. Development/test intentionally accept weaker identity/role authority; correct `APP_ENV` is essential.
3. Server-owned workspace/Phase 4 authority → `telemetry_scope.py` → scoped connection/signal/hierarchy services → PostgreSQL telemetry repository and V2 execution/lineage repositories. The repository uses complete scope predicates and bound SQL parameters; IDs alone are not authority. Historical uploads instead use dataset-scoped storage, upload-state repository, runtime DB and generated filesystem keys; retained production uses shared object state and PostgreSQL. This is application isolation inside shared infrastructure, not independent tenant containers/databases.
4. Repository/canonical observations → SII/Phase 4 analytical engine → stored evidence, canonical artifacts and provenance → authenticated scoped results/replay/evidence/findings/export. `evidence_store.py`, `finding_workflow.py`, runtime DB and `routers/evidence.py` enforce scope. Failed-evidence customer projection is separated from authenticated-admin, scoped, audited forensic retrieval; stored bytes are preserved. Hashes detect disagreement within trusted storage, not replacement of both artifact and expected hash by an administrator. Ecosystem/distributed-cognition routes use authenticated current-upload reads; their readiness adapters are descriptive code, not proof of an OT permission boundary.
5. Customer telemetry replica/provider → HTTPS retrieval connector → production `RemoteHttpsTelemetryConnector` → private TLS executor `/v1/connector-jobs` → HMAC/replay checks → root broker resolves server-owned secret binding → UID/GID 10002 child with scrubbed environment → GET-only HTTP client → bounded page → ingestion normalization/quarantine/deduplication → canonical observations → PostgreSQL. The current remote client/broker allow only `bfzcudq5o2.execute-api.us-east-2.amazonaws.com`, an approved synthetic endpoint, not arbitrary customer equipment. Customer expansion requires recertification. Historian registry is empty by default; protocol placeholders (Modbus, OPC UA, MQTT, BACnet) have no functional provider. Legacy REST/database/global telemetry routes return 410 outside development/test, and legacy pollers are disabled in shared environments.
6. CI → SHA-pinned actions and dependency audits (`.github/workflows/ci.yml`) → container build → ECR digest → manual `deploy-backend.yml` → `scripts/production_release.py` source/overlay/profile verification → image-only ECS deployment. Production runtime is frozen to an existing certified image, rather than rebuilt solely from current root Dockerfile. Release guards preserve task topology, roles, secret bindings and egress configuration. Runtime/source security changes require separate release recertification. Long-lived AWS workflow credentials remain a distinct privileged boundary.

## Read-only / OT and tenant conclusions

Application prohibition is IMPLEMENTED and relevant operation/SSRF controls are TESTED. Child network restriction is IMPLEMENTED in `infra/production/connector-executor-user-data.sh`; retained production evidence reports Network Firewall READY/IN_SYNC. Customer credential and protocol prohibition are UNVERIFIED. A compromised child has the resolved upstream credential and could emit arbitrary HTTPS methods within its allowed destination; a compromised broker runs as root and retains AWS secret access. A compromised API holds authority to sign connector jobs. Thus **“a compromised Neraium service cannot actuate” is not established by GET-only code**. No customer control network should be reachable; use a replica/export service whose identity cannot write, and enforce that independently.

Workspace isolation is stronger than client-supplied IDs: explicit membership maps to immutable scope; systems/assets/signals/mappings/connections inherit that facility authority. Historical dataset IDs are resolved inside dataset scope; findings, evidence, investigations/workflow and exports resolve scoped records. No independent organization-admin security model was established: auth users/roles are platform-global, with facility membership supplying customer resource separation. Do not grant customer users platform-admin privileges. Membership does not independently grant a per-system confidentiality boundary within a facility.

## Ingestion and runtime assessment

Uploads are streamed with aggregate and file limits; filenames do not become storage paths. No upload archive extraction was located in these supported intake paths. Telemetry contracts bound config, metadata, pages, records, retries and backfill; non-finite values and invalid timestamps receive controlled dispositions. Duplicate detection is not a bandwidth/CPU quota. Finite extreme values and source truth remain governed analytical questions; no numeric/timestamp semantics were changed.

Safe isolated decompression check: HTTPX decoded a 97-byte gzip response into one 65,536-byte chunk before caller iteration. This confirms the allocation-before-cap mechanism without a large workload or network contact. A bounded decoder or a compatibility-reviewed rejection of compressed responses is required; changing accepted provider encoding was not treated as a low-risk audit fix.

Retained evidence: `docs/operations/production-deployment-recertification-2026-10-03.md`, `first-customer-production-baseline-2026-10-03.json`, SRE closeout and Production V2 release report. They report API/worker revisions 339/333 at an immutable image digest, tasks with public IP assignment disabled, CA-verified private executor health, firewall readiness, encrypted/deletion-protected RDS with seven-day backups, successful restore drill and 17 configured alarms with confirmed SNS receipt. Retained V2 grant evidence denies runtime superuser/role/database creation, schema CREATE and migration-ledger writes. These facts are not fresh live verification of all SG/IAM/TLS/CloudTrail controls.

The executor script uses host networking, a root broker with SETUID/SETGID, read-only filesystem and no-new-privileges; child UID egress includes DNS and approved public IP:443, with private/metadata and IPv6 denial. DNS resolution allows traffic sharing an approved endpoint IP; it is not a method/credential permission firewall. API/worker immutable-image lineage, effective capabilities/rootfs, ECR scanning results, secret resource policies, CloudTrail coverage and backup KMS principals still require review.

## Required actions before admitting a customer pilot

1. Supply explicit upstream role/API policy showing no command/write permission; use a read-only replica or export gateway with no control-network route. Keep supported connector protocols/operations and destination list fixed until reviewed recertification. Enforce method/resource restrictions at the gateway, including paths/query parameters with side effects. Verify denied writes with a customer-approved harmless permission check, not an equipment command.
2. Review effective ECS task/execution and executor instance policies: exact secret ARNs, `GetSecretValue`/`DescribeSecret` only where needed; no connector Create/Put/DeleteSecret; scope KMS decrypt by key and Secrets Manager context. Separate platform/bootstrap DB authority from runtime credentials. Verify secret tags/resource policies and backup principal access. Do not infer safety from environment flags.
3. Verify actual SG/routes/Network Firewall rules for API, worker and broker: no OT/private-control destination, default-deny egress with explicit AWS endpoint/DB/executor/telemetry exceptions. Restrict executor ingress to its caller SG. Verify ALB TLS policy/certificate/HTTPS redirect, private RDS ingress, database `verify-full` with trusted CA, S3 public-access block/encryption/retention, and audit/CloudTrail retention. These are recommendations, not changes made here.
4. Establish ingress timeouts, per-tenant distributed rates, atomic queue limits, executor concurrency and CPU/memory/temp/storage quotas. Address upstream decompression and subprocess output limits. Until then keep pilot ingestion rates low and agreed, with monitored abort thresholds; idle metrics are not capacity qualification.
5. Restrict global admin/service-token use and workspace allowlists. Protect the auth DB/backups as bearer stores pending a reviewed token-at-rest migration; require strong administrative authentication operationally. Verify production `APP_ENV`, trusted proxy list and exact CORS origins. Verify hosted frontend CSP/security headers and cache/workstation retention.
6. Review the exact runtime dependency/OS inventory with current scanners before release; retain SBOM and scan results. Replace long-lived deployment keys with scoped OIDC; activate secret scanning, SAST and container gates; represent protected release approvals. A repository pin is not proof of hosted branch protection.
7. Separately recertify and release the executor body-limit fix using the governed release process. No audit finding authorizes production mutation.
